Rename…, pressed on a playlist's own ⋯ in the running app, against a demo iPod
that ipod-sync.sh actually wrote to. Every line below is read back off the
volume after the press, not asserted about it: accepting a confirmation runs
the real ipod-remove.sh against the device.

Reproduce with:
  Xephyr :77 -screen 1300x900 -dpi 96 -br -noreset &
  DISPLAY=:77 .no-mistakes/evidence/refuse-stranding-playlist-rename/\
run-scenarios.sh . /tmp/rename-out

The machine differs in one thing only: whether the PATH the app and the scripts
are given has a speech engine on it. Nothing is stubbed; has_speech_engine asks
that PATH, exactly as it does for a user.

1. BEFORE (pre-change ipod_gui/playlist_view.py), no speech engine,
   "Morning Ride" - 2 tracks, on the iPod
     confirmed:  "...removes the old one. ... The new name cannot be staged
                  until one is installed, so the playlist leaves the iPod and
                  does not come back."
     volume:     ['Morning Ride.m3u'] -> []          <- taken off the iPod
     spoken:     2 recordings -> 0
     queued:     nothing
     said:       "Renamed to Evening Ride · not queued: no speech engine
                  installed", then "Playlist removed"
   The playlist is off the device, nothing is queued to put it back, and Send
   to iPod wants the same engine staging does. Stranded until an engine is
   installed and the user works out they have to send it again.

2. AFTER, same machine, same playlist
     no dialog opened
     said:       "No speech engine installed, so renaming Morning Ride would
                  take it off the iPod with nothing able to put the new name
                  there"
     volume:     ['Morning Ride.m3u'] -> ['Morning Ride.m3u']   <- untouched
     spoken:     2 recordings -> 2
     here:       Morning Ride.m3u still under its own name
     no script ran: the app's output pane is empty

3. AFTER, no speech engine, "Old Mixtape" - 0 tracks, on the iPod
   (the carve-out: synced once, emptied here since)
     confirmed:  "...removes the old one. This playlist lists no tracks, so
                  nothing is staged to replace it. With no speech engine
                  installed, the rebuild that removal runs leaves the iPod's
                  spoken names gone."
     volume:     ['Morning Ride.m3u', 'Old Mixtape.m3u'] -> ['Morning Ride.m3u']
     here:       Old Mixtape.m3u -> Old Mixtape Revived.m3u
     queued:     nothing, and nothing needs to be
   Refusing this one is what the goal warns about in the other direction: the
   old empty name would sit on the iPod as a device-only playlist, and nothing
   automatic would ever take it off again.

4. AFTER, with a speech engine, "Morning Ride" - 2 tracks, on the iPod
     confirmed:  "...removes the old one and stages the new name for the next
                  sync."
     volume:     ['Morning Ride.m3u'] -> []
     queued:     Evening Ride.m3u    <- the new name, for the next sync
     said:       "Renamed to Evening Ride · queued for sync", then "Playlist
                  removed"
   Both halves of the rename happen, which is the case the refusal exists to
   distinguish itself from.

5. AFTER, no speech engine, "Downloads" - 2 tracks, NOT on the iPod
     confirmed:  "The name is what the iPod will say out loud."
     volume:     ['Morning Ride.m3u'] -> ['Morning Ride.m3u']   <- untouched
     here:       Downloads.m3u -> Downloads Sorted.m3u
     said:       "Renamed to Downloads Sorted · not queued: no speech engine
                  installed"
   Never refused: the refusal is about what the iPod would be left holding,
   not about the engine.

6. AFTER, the README's other half: where Rename… is, read off the menus
   ("--menu-only", which presses nothing)
     a playlist made here      the ⋯ on its page offers Rename…, Delete…
     one only the iPod holds   the ⋯ on its page offers Remove from iPod…
   Which is also why the refusal names no way out: the row a rename would
   strand has no "Remove from iPod" of its own, and its Delete would take the
   file here with it.
